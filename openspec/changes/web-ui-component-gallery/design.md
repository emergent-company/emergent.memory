## Context

Reusable templ components live in two places: the shared `components` package (24 shipping templ components — 20 exported plus 4 private helpers, alongside the `DialogAutoOpen` attributes helper; 2 further `^templ` defs are test-only fixtures) and shared composites written inline in `package main` (89 exported templ funcs, 75 of them `*Page`). The app also renders hundreds of go-daisy primitives. There is no catalog, no dependency view, and no preview surface; `web-ui-component-conventions` requires visual verification "through the component gallery" but the gallery does not exist.

go-daisy's upstream module ships a reusable gallery (`galleryruntime`) plus dev-mode boundary helpers (`devmode`); the vendored tree in this repo carries only `components/`, `devmode/`, `render/`, `shared/`, and `staticfs/` — no `galleryruntime` and no `cmd/gallery`. Upstream's `galleryruntime` page components and registry types are exported, but it exposes no mountable Echo handler — its only entry point, `Serve(...)`, starts its own blocking server — and its ~11,000-line fixture seed (`cmd/gallery/internal/gallery`, `seed.go` 9,814 + `seed_additions.go` 1,140) is an `internal` package that cannot be imported. Generated `*_templ.go` files render each component as an ordinary Go call (`ui.Button(...)`, `components.PanelCard(...)`), which makes static call-site analysis tractable. See proposal.md — Why.

## Goals / Non-Goals

**Goals**
- One dev-gated page, inside the app shell, listing reusable components with metadata and a dependency view.
- A deterministic, generated dependency graph derived from render call sites.
- Isolated, render-only fixture previews that cannot drive the app.

**Non-Goals**
- Cataloging every templ function (pages, page-private helpers) — spec scope is reusable components only.
- Auto-generating fixtures; the long tail uses an authored zero-value closure and is flagged when empty or panicking.
- Replacing Playwright visual coverage; the gallery complements it.
- Enabling the gallery in production by default.

## Decisions

**Native page, not an embedded `galleryruntime` server.** `galleryruntime` cannot mount into the existing Echo router (its `register` is unexported and the only entry point starts a second server) and its fixture seed is unimportable, so reuse would still require authoring a registry — while leaving the gallery outside the app shell, outside its auth, and without a dependency graph. We adopt its useful patterns (iframe isolation, story variants) in a native page. Alternatives: run the upstream gallery as a separate dev server (rejected: outside the app, no dependency graph, duplicate fixtures); fork `galleryruntime` into the repo (rejected: vendoring maintenance for no behavioural gain).

**Scope is an explicit, test-pinned seed list.** "Shared composite" has no objective source-level signal: of the 89 exported `package main` templ funcs, 75 are `*Page`, and several of the remaining 14 are exported but used by only one page feature (e.g. `BoardColumns`, `ShareLinksHeader`). The registry therefore carries a hand-maintained seed, and a component earns a place only when reused across two or more page features or when it encapsulates an invariant — mirroring the existing "a component earns its place" convention. Operationally, a `package main` candidate is in scope when the generated used-by edges reach two or more distinct L4 page components (direct static call edges), or when the entry documents an encapsulated invariant; L3 page-local helpers are excluded by layer regardless of call count. This is the app-level interpretation of the conventions spec's "two or more call sites" rule. A unit test pins the seed and the exclusion of page/private helpers.

**Static `go/ast` graph over generated templ Go plus hand-written factories.** Component renders are ordinary calls in the generated `*_templ.go` files, so a two-pass scan (collect component definitions, then walk bodies for calls into the known component set) yields edges, reverse edges, the individual go-daisy component references (which become L0 catalog entries and `uses` targets), and the go-daisy packages rendered (for the external-dependency field). The definition pass MUST read both the generated `*_templ.go` and the hand-written `.go` files in the gateway packages, because components also exist as hand-written factories (`flashToast`, `partialWithTitle` in `ui.go`) that generated pages call; it MUST select only functions whose exact return type is `templ.Component` (excluding `templ.Attributes`/`templ.ComponentScript`/`templ.CSSClass` returners) and MUST exclude `*_test.go` so test-only fixtures never enter the catalog. Same-package unqualified calls MUST resolve within the package; an unresolved same-package callee is recorded as a package-granularity leaf rather than a dangling edge. go-daisy nodes and packages are derived only from the gateway's own call sites and import aliases — the generator never scans go-daisy source (`vendor/` is gitignored and absent on a fresh checkout) — and go-daisy entry metadata (props/description/fixtures) is hand-curated in the seed. The walk MUST unwrap the shapes templ actually emits: the component call is the receiver of `.Render(...)` (e.g. `components.PanelCard(...).Render(templ.WithChildren(ctx, …), buf)`), so the scanner matches the `X` of a `X(...).Render(...)` `SelectorExpr`, including the `templ.WithChildren` first-argument form. Component-typed parameters render as `param.Render(ctx, buf)` and are inherently dynamic. The scanner MUST resolve each file's import aliases to packages — including unaliased imports (`nav`, `table`, `layout`) and the same package imported under two aliases (`fm "…/components/form"` vs `form "…/components/form"`) — and MUST also collect hand-written `templ.ComponentFunc` components, which return `templ.Component` from a literal rather than a generated top-level func. Crucially, used-by requires scanning every gateway templ file, including pages and helpers that are not catalog entries: the shared `components` package is invoked only from `package main` pages, so an entries-only scan would report no callers. Used-by is aggregated per call site (page feature), and page call sites may appear in used-by even though pages are not catalog entries. The call graph is a general directed graph and MAY contain cycles (mutual L3↔L3 renders), so consumers (used-by, dependency panel) MUST use a visited-set and MUST NOT assume a DAG or topological order; the import graph remains acyclic (L4→L3→L2→L0). This needs no new dependency and is deterministic. Alternative: templ's `parser/v2` (works but adds parsing wiring for the same result); `devmode` runtime boundaries (would require wrapping every component and captures only what is rendered in a given fixture, not the full static graph). Limitation: components rendered dynamically (component-typed params) or via `templ.Raw` are not captured; the registry supports a manual `AdditionalUses` escape hatch and a test pins known edges.

**Iframe isolation for previews.** Dialog, dropdown, toast, and command-palette components, plus duplicate ids across many previews, make inline rendering unsafe and visually misleading. The preview route returns a slim standalone document that links only the app's compiled stylesheet (`webui.AssetPath("/css/app.css")` under `/assets/`) and renders the fixture on a neutral canvas. It loads no client scripts in this change, so previews are render-only: component markup is shown under real CSS without executing htmx or Alpine, which keeps a preview from driving the app. Scripted/interactive previews (opening dialogs, dropdowns, toasts) are a deliberate follow-up.

Previews MUST NOT be able to mutate the backend. The session cookie is `SameSite=Lax`, so a same-origin iframe carries it on subresource and form requests, and the rendered fixtures include real forms and dialogs. The preview iframe therefore carries `sandbox=""` — no scripts, no forms, no same-origin — so an opaque origin sends no cookie and any POST fails harmlessly. Previews are render-only: this change does not execute client scripts in a preview, so a component that would open a dialog, dropdown, or toast shows its static markup rather than an interactive overlay. Fixtures SHALL use inert content: `href="#"`, `type="button"` buttons, no live endpoint ids, and no real mutation wiring. Alternative: render inline in the gallery page (rejected: overlay escape, id collisions, and no sandbox boundary).

**Curated fixtures plus an authored default render.** Authoring fixtures for every component is week-scale effort. There is no generic way to call an arbitrary typed templ func with zero values, and zero values are not always safe (`ListRow("", nil, "", "")` dereferences a nil `templ.Component`; `PanelCard("", nil)` behaves likewise). Every catalog entry therefore carries an explicit `Render func() templ.Component` closure; entries without a curated fixture get an authored zero-value closure. Empty-detection runs the closure inside a `recover()`, so a nil-slot panic is reported as "needs fixture" rather than crashing the gallery. "Empty" means no non-whitespace text and no element in the rendered output. This keeps the catalog useful immediately and honest about coverage.

**External dependencies come from two sources.** Both the per-component go-daisy references (L0 entries + `uses` edges) and the package-level go-daisy usage (external deps) come from the generated static graph; client wiring (Alpine `x-*`, Stimulus `data-controller`, htmx `hx-*`, and custom `data-*` markers) is detected by scanning the component's `.templ` source body, not the rendered fixture HTML — zero-value or partial renders do not emit every marker, so HTML-based detection would under-report.

**Config gating, not role gating.** The gallery is a developer tool, not an org-admin concern. `MEMORY_COMPONENT_GALLERY` is an explicit flag, **default off in every mode**; when unset, routes 404 and no navigation entry renders. There is no `AuthMode`-based default because `task dev` runs in `AUTH_MODE=session` (like the public dev deployment), so an auth-mode default would be off exactly where a developer needs it. Instead the dev environment and the e2e/dev harness set the flag on. Rollback is unsetting the flag.

**Generator lives at `cmd/componentgraph` in the gateway module.** `go:generate` writes `devgallery_graph_gen.go` into `package main`, so the graph and the registry are compiler-checked together and no generated file needs to be hand-edited. The generator reads source text (`*_templ.go` + hand-written `.go`), which are build products, so `go generate` MUST run after `templ generate` in both the dev loop (`task dev`/air) and CI; the staleness test (task 2.5) regenerates post-`templ generate` and MUST NOT skip when `vendor/` is absent, since it does not need go-daisy source. `cmd/componentgraph` is covered by the gateway's `./...` build/vet/lint.

**Dev routes bypass project scoping.** `/dev/components` is not project-scoped. The default project-resolution middleware (`projectScopePath`/`resolveDefaultProject`) would otherwise 302 a dev with no active project to `/orgs`, or re-issue the session cookie as a side effect, and `canonicalHostRedirect` would bounce it off a non-canonical host. The `/dev/` prefix is therefore exempted from project scoping and from the canonical-host redirect, alongside the existing public/static exemptions.

## Risks / Trade-offs

- **Generator misses dynamic renders** → the walk unwraps `X(...).Render(...)`/`templ.WithChildren` but component-typed params and `templ.Raw` remain uncaptured; the registry supports a manual `AdditionalUses` field and a unit test asserts known edges (e.g. a composite → `ui.Card`).
- **Fixtures drift as components change** → fixture functions are typed Go against the components, so prop changes fail the build; an e2e test asserts each listed slug's preview renders non-empty.
- **Default-off gate hides the gallery from the Playwright run** → the gallery spec is excluded from the session-mode `chromium` project (whose external gateway leaves the flag off) and runs under a dedicated flag-on harness config (`tests/e2e/dev-gallery.config.ts`), which starts the in-repo dev harness (`tests/e2e/run-e2e.sh`, `AUTH_MODE=dev`) that exports `MEMORY_COMPONENT_GALLERY=on`.
- **go-daisy upgrade changes the used set** → the graph is regenerated; the go-daisy entry list derives from edges, so it tracks automatically.
- **Many iframes on one page** → previews use `loading="lazy"` and detail rendering is on demand.
- **Generated files are stale in CI** → a check regenerates the graph and fails if it differs (covered by a task).

## Migration Plan

Additive; no data or API migration. The flag is off by default, so a deployment opts in explicitly: the local dev `.env` (documented commented/off in `.env.example`) and the in-repo e2e/dev harness set `MEMORY_COMPONENT_GALLERY=on`; production leaves it unset. Rollback is unsetting the flag (routes 404 after auth, no other behaviour affected).
